01Overview

A coding agent is dropped into an isolated container holding a minimal, boot-verified copy of the benchmark, the task, and an empty workspace — and asked to write a program that makes the robot solve the task.

Getting there is four procedures — build the docker images once per machine, build each world once, run any number of agents against it, and grade what they submit. Each has its own tab above; the whole flow:

  1. 1
    once per machineBuild the docker images

    The simulator and the agent CLIs, installed into reusable images. The benchmark is never baked in — an image knows nothing about any task.

  2. 2
    once per worldBuild the world

    Copy only the benchmark files this task needs. Ablations start here: some functions (e.g. snapshot restore) can be blocked in the copied code. One world serves a whole series of runs; a different ablation is a separate build.

  3. 3
    once per runRun the agent

    A disposable container: the world read-only, one writable workspace, guarded network. The prompt is assembled here — hints that ease the task, rules that disclose what the build blocked. At the deadline the container dies; the workspace survives.

  4. 4
    once per deliveryGrade

    The delivered solve.py is replayed in a second isolated container — the same world (its restrictions still bind), plus the private grader, no network. The agent may do anything during its run; only what passes here counts.

Quick start

# 0 · host setup, once — two prerequisites: # the repo's .venv (robobench + Isaac Lab installed; used by build_env's boot check) # docker + NVIDIA container toolkit + CDI (eval/docker/INSTALL.md) # 1 · build the images, once # l0 = Isaac baked venv (30–60 min) · warm = shader cache · l1 = agent CLI layer make -C eval/docker l0 make -C eval/docker warm make -C eval/docker l1 CC_VERSION=$(npm view @anthropic-ai/claude-code version) # 2 · build a world (~90 s) python3 eval/scripts/build_env.py --name bulb_fable --stage bulb:franka # 3 · run one agent in one disposable container (inside tmux) # credential from `claude setup-token` — or export ANTHROPIC_API_KEY instead export CLAUDE_CODE_OAUTH_TOKEN=… python3 eval/scripts/run_agent.py experiments/bulb_fable --model claude-fable-5 --budget-min 120 # 4 · watch live — artifacts land in experiments/bulb_fable/runs/<r>/ # deliverable: workspace/solution/solve.py · prompt: task/ · record: run.json tail -f experiments/bulb_fable/runs/<r>/workspace/.agent/transcript.jsonl

From here, 02 · Examples is the cookbook: ablation variants, run settings, and model comparisons.

What keeps it honest

Tasks come from registered, verified configs Every registered scene–robot pairing has been solved at least once, so an agent is never handed an impossible world.
Nothing to cheat with The container holds no solutions, no graders, no demo scripts; the benchmark is read-only and the network reaches only the model API and the package index.

02Examples

Five complete usage patterns. The grammar is always the same: world-level choices are build_env flags (one build per variant), prompt-level choices are condition yamls, and runs repeat N times with everything archived under experiments/<world>/runs/.

1 · Different agents and models

Which agent solves the task, and at what token cost — everything else held fixed.

# one world, then vary only the agent/model — nothing else changes python3 eval/scripts/build_env.py --name bulb --stage bulb:franka python3 eval/scripts/run_agent.py experiments/bulb --model claude-fable-5 --run fable1 python3 eval/scripts/run_agent.py experiments/bulb --model claude-opus-5 --run opus1 python3 eval/scripts/run_agent.py experiments/bulb --agent codex --model <id> --run codex1 # repeat with --run fable2, fable3, … · budget and GPU are also per-run knobs: python3 eval/scripts/run_agent.py experiments/bulb --model claude-fable-5 --budget-min 60 --gpu 1 --run quick1

2 · Different scene + robot

Coverage: the same harness runs every registered task; nothing is bulb-specific.

# a world is a REGISTERED scene:robot pairing — the registry is the task menu python3 eval/scripts/build_env.py --list python3 eval/scripts/build_env.py --name bulb_franka --stage bulb:franka python3 eval/scripts/build_env.py --name nut_franka --stage nut_thread:franka python3 eval/scripts/run_agent.py experiments/nut_franka --model claude-fable-5 # an unregistered pairing refuses to build, printing the menu (feasibility gate): python3 eval/scripts/build_env.py --name x --stage bulb:aloha

3 · Interactive — work with the agent in its sandbox

A live session you can join and leave. The default condition (configs/interactive.yaml) tells the agent to work as autonomously as possible — a human may occasionally check results and leave feedback, and the agent must never idle waiting for one. Useful for coached solving, debugging a world, or demos.

# build a world, then open a live session inside its sandbox python3 eval/scripts/build_env.py --name bulb --stage bulb:franka export CLAUDE_CODE_OAUTH_TOKEN=… python3 eval/scripts/run_interactive.py experiments/bulb --model claude-fable-5 --run pair1 # join it — from any terminal, any time (the launcher prints this line too) docker exec -it rb_bulb_pair1 runuser -u agent -- tmux attach -t agent # leave WITHOUT stopping the agent: Ctrl-b d # SSH dropped / terminal closed? nothing was lost — find the container and re-attach: docker ps --filter name=rb_ docker exec -it rb_bulb_pair1 runuser -u agent -- tmux attach -t agent # finish for good (workspace + run.json stay on the host under experiments/bulb/runs/pair1/) docker stop rb_bulb_pair1

4 · Controller ablation — tiers, and a custom-controller variant

How much does the controller abstraction help — and can the agent do better with its own?

# tiers are different registered presets (third slot of --stage); # each world is frozen to its own mode — switching raises inside it python3 eval/scripts/build_env.py --name bulb_osc --stage bulb:franka:osc python3 eval/scripts/build_env.py --name bulb_joint --stage bulb:franka:joint python3 eval/scripts/run_agent.py experiments/bulb_osc --model claude-fable-5 --run t1 python3 eval/scripts/run_agent.py experiments/bulb_joint --model claude-fable-5 --run t1 # custom-controller variant: unfreeze the world, and (optionally) teach the topic # with a condition yaml: hints: [custom_controller] python3 eval/scripts/build_env.py --name bulb_free --stage bulb:franka --no-freeze-controller python3 eval/scripts/run_agent.py experiments/bulb_free --config eval/prompts/configs/custom_controller.yaml # gains and strategy are free in EVERY variant — the freeze only gates mode switching

5 · Snapshot ablation

Does rollback ability change success and cost?

# two worlds: identical, except env.set_states() raises in the second python3 eval/scripts/build_env.py --name bulb --stage bulb:franka python3 eval/scripts/build_env.py --name bulb_nosnap --stage bulb:franka --no-set-states # with snapshots — the default condition ships the save_snapshot hint python3 eval/scripts/run_agent.py experiments/bulb --model claude-fable-5 --run snap1 # without — the block is disclosed via rules: [no_set_states, …] # (selecting the snapshot hint against this world refuses to launch) python3 eval/scripts/run_agent.py experiments/bulb_nosnap --config eval/prompts/configs/nosnap.yaml --run nosnap1

6 · Transfer — carry skills across scenes or robots

Do success rate and token efficiency improve on a later task, given the earlier task’s artifacts?

# scene transfer: same robot, new scene — does screwing skill carry? python3 eval/scripts/build_env.py --name screw_seq --stage bulb:franka --stage nut_thread:franka # robot transfer: same scene, new embodiment (both pairings must be registered) python3 eval/scripts/build_env.py --name embody_seq --stage nut_thread:franka --stage nut_thread:<robot2> # run: one fresh session per stage; stage 02 inherits a COPY of stage 01's # workspace (minus .agent/ telemetry) — continuity is files, never context python3 eval/scripts/run_sequence.py experiments/screw_seq --model claude-fable-5 --config eval/prompts/configs/transfer.yaml # disclosed variant: condition selects leave_handoff — early stages write HANDOFF.md # (auto-dropped on the final stage) # undisclosed variant: same command, condition without leave_handoff # baseline: build nut_thread:franka alone and run it cold — # equal tree hashes prove the worlds matched

03Build the docker images

Everything an agent run needs except the benchmark itself, baked once into layered images: the Isaac simulator stack in a ready venv, and the agent CLIs on top. Benchmark changes never require a rebuild.

04Build the experiment folder

One command turns a registered task into a self-contained, boot-proven folder on disk — the world the agent will later be locked into. It produces the world only (prompts are assembled per run, §05), and everything environmental fails here, at build time — at agent time, a failure is the agent’s.

# requires the repo's .venv (robobench + Isaac Lab) — but no activation: # the script re-execs itself into it python3 eval/scripts/build_env.py --name bulb_smoke --stage bulb:franka # --list show all registered presets # --stage scene:robot[:controller] — controller defaults osc > impedance > joint # --no-set-states ablation: disable snapshot-restore; solve from reset() forward # --no-freeze-controller allow switching control modes (default: frozen to the preset) # transfer test: repeat --stage to build an ordered sequence — e.g. skills carried to a new scene: python3 eval/scripts/build_env.py --name screw_transfer --stage bulb:franka --stage nut_thread:franka # each stage gets its own bench/; the agent keeps its workspace files from stage 01 into stage 02

What it does

resolveintent → registered preset, else fail with the menu of what exists
extractminimal benchmark tree: no other suites, no demo scripts, only the assets this task needs; solve-provenance comments scrubbed
patchone-time edits to the copied code that block functions the agent could otherwise exploit — control-mode switching (blocked by default), snapshot restore (--no-set-states). The mount is read-only, so a block cannot be undone.
boot-provelaunch the sim from the extracted tree and reset the actual preset — no world ships unbooted
receiptcontent hash + repo revision + argv, so every result is attributable to exact code

What lands on disk

experiments/bulb_smoke/ ├─ resolved.json receipt: argv · preset · hashes · repo revision ├─ MANIFEST human-readable summary ├─ stages/01_bulb_franka/ │ ├─ bench/ minimal benchmark tree, boot-proven (~141 MB for bulb) │ └─ describe.md scene + robot description, harvested at boot └─ runs/ created later, one per agent run

The receipt — facts that every run must respect

resolved.json ├─ name · argv · set_states what was built, and with which ablations └─ stages[]: preset · assets · tree_sha256 world identity — equal hashes = same world control_mode_frozen · boot_checked

The receipt is what keeps prompts honest downstream: at launch, a selected rule/hint is checked against these facts — e.g. the no_set_states rule refuses to render against a world whose receipt says snapshots are enabled.

05Run experiments

A run pairs one built world with one prompt condition. The world is fixed; the condition is chosen per run — so a single experiment folder hosts many runs under different conditions, all against the byte-identical tree. Two runners: run_agent.py for single tasks, run_sequence.py for staged sequences. One run = one disposable container, killed at its budget.

# credential — from your shell, never stored (or ANTHROPIC_API_KEY / OPENAI_API_KEY) export CLAUDE_CODE_OAUTH_TOKEN=… # run with the default condition (eval/prompts/configs/default.yaml) … python3 eval/scripts/run_agent.py experiments/<exp> # … or with a chosen condition yaml python3 eval/scripts/run_agent.py experiments/<exp> --config eval/prompts/configs/<cond>.yaml # the CLI is infrastructure only: --agent claude|codex · --model … · --gpu N · --budget-min … · --dry-run # hints / rules live ONLY in the condition yaml — authored, never ad-hoc flags # run_agent = the default runner (one scene + one task); sequences: run_sequence.py, see §02

The /task folder — assembled fresh for every run

runs/<r>/task/ mounted ro at /task; instructions.md is fed to the agent CLI ├─ instructions.md the contract verbatim (+ carryover note on stage 02+) ├─ task.md auto-generated: scene + robot description, goal, build snippet ├─ rules/… selected disclosures — never automatic └─ hints/… selected hints; both libraries live in eval/prompts/

Everything except the auto-generated task.md is hand-authored library content, selected by the yaml. The prompt may withhold but never lie: a selection contradicting the world's receipt refuses to launch — restrictions themselves are baked at build time, the runner only discloses them. run.json records the full condition.

The prompt libraries (eval/prompts/)

wherewhatcurrent contents
configs/run conditions — which hints/rules a run getsdefault · interactive · nosnap · custom_controller · transfer
rules/binding disclosures, one file eachautonomous_operation · leave_handoff · no_set_states* · frozen_controller*
hints/optional guidance, one file eachsave_snapshot* · custom_controller*
_contract.mdthe fixed instructions every agent reads firstenvironment · /task semantics · solve(env) deliverable

* = named placeholder, content pending. A rule/hint that presumes a world fact (e.g. no_set_states) is validated against the receipt at launch.

Sequences — run_sequence.py

python3 eval/scripts/run_sequence.py experiments/<multi-stage-exp> --config eval/prompts/configs/transfer.yaml # one FRESH session per stage, strictly in order; budget applies per stage # stage N+1's workspace = a COPY of stage N's final workspace, minus .agent/ telemetry # the leave_handoff rule (if selected) is dropped automatically on the final stage # artifacts: runs/<seq>/<stage>/{task,workspace,container.log,run.json} + sequence.json

Interactive — pair with the agent inside the sandbox

python3 eval/scripts/run_interactive.py experiments/<exp> [--config …] [--model …] # default condition: configs/interactive.yaml — run autonomously; a human may check in with feedback # the agent CLI runs interactively in a tmux session inside the container: # attach: docker exec -it <container> runuser -u agent -- tmux attach -t agent # detach: Ctrl-b d — the session keeps running; stop: docker stop <container> # same world, mounts, and /task as a headless run — but you can watch and type # feedback anytime. Note: interactive turns wait for a human, so timings and # budgets from these sessions are not comparable with run_agent results.

The container contract — what the agent sees

stages/01_…/bench/
→ ro
/bench import robobench = this tree, nothing else
runs/<r>/task/
→ ro
/task the per-run prompt folder (instructions · task · rules · hints)
runs/<r>/workspace/
↔ rw
/workspace the only writable dir; visible on the host live
docker volume rb-ovcache
↔ rw
/ovcache shared shader cache
baked in the image, not mounted: /opt/venv (Isaac) · agent CLIs — and nothing of the repo

The repo, your experiments, solutions, and .git do not exist inside the container. run_agent.py is open-network for development; measured runs go through compose.agent.yaml, whose egress allowlist admits only the model API and the package index (GitHub blocked).

06Grade

The delivered solve.py replays in a second isolated container: the same image and read-only world the agent had, plus the suite's private grader — never in any agent-facing tree. No credentials; --network none grades fully offline. One trajectory per grade for now.

Grade a delivery

python3 eval/scripts/run_grade.py experiments/<exp> --run <run> # grades runs/<run>/workspace/solution/solve.py → runs/<run>/grade/ python3 eval/scripts/run_grade.py experiments/<exp> --solution <dir> --out <dir> # any explicit delivery # flags: --gpu · --network · --budget-min · --dry-run

The graded run

Fresh env, the grader's reset — solve() gets a GradedEnv: same surface, but every step is scored into the curve, and reset / set_states raise. When it returns, the verdict reads the final state.

Artifacts — <out>/

verdict.json
→
the verdict success · score (peak progress) · solve wall/sim time
progress.jsonl
→
the curve one record per step: sim_time_s · wall_s · progress · per-stage values
grade.json · container.log
→
the record launch parameters + raw output

Graders live in robobench/suites/<suite>/grader/, one module per scene in its GRADERS dict. A new grader = a docstring + a weighted RUBRIC + one method per stage. Session cost/tokens come from collect_metrics.py, not the grade.
