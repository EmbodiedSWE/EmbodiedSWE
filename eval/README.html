01Overview

A coding agent is dropped into an isolated container holding a minimal, boot-verified copy of the benchmark, the task, and an empty workspace — and asked to write a program that makes the robot solve the task.

Getting there is four procedures — build the docker images once per machine, build each world once, run any number of agents against it, and grade what they submit. Each has its own tab above; the whole flow:

  1. 1
    once per machineBuild the docker images

    The simulator and the agent CLIs, installed into reusable images. The benchmark is never baked in — an image knows nothing about any task.

  2. 2
    once per worldBuild the world

    Copy only the benchmark files this task needs. Ablations start here: some functions (e.g. snapshot restore) can be blocked in the copied code. One world serves a whole series of runs; a different ablation is a separate build.

  3. 3
    once per runRun the agent

    A disposable container: the world read-only, one writable workspace, guarded network. The prompt is assembled here — hints that ease the task, rules that disclose what the build blocked. At the deadline the container dies; the workspace survives.

  4. 4
    per submission · openAuto-grade

    The submitted solution is replayed in a second isolated container — the exact same world, plus the private verifiers. The agent may do anything during its run; only what passes here counts. Details still undecided.

Quick start

# 0 · host setup, once — two prerequisites: # the repo's .venv (robobench + Isaac Lab installed; used by build_env's boot check) # docker + NVIDIA container toolkit + CDI (eval/docker/INSTALL.md) # 1 · build the images, once # l0 = Isaac baked venv (30–60 min) · warm = shader cache · l1 = agent CLI layer make -C eval/docker l0 make -C eval/docker warm make -C eval/docker l1 CC_VERSION=$(npm view @anthropic-ai/claude-code version) # 2 · build a world (~90 s) python3 eval/scripts/build_env.py --name bulb_fable --stage bulb:franka # 3 · run one agent in one disposable container (inside tmux) # credential from `claude setup-token` — or export ANTHROPIC_API_KEY instead export CLAUDE_CODE_OAUTH_TOKEN=… python3 eval/scripts/run_agent.py experiments/bulb_fable --model claude-fable-5 --budget-min 120 # 4 · watch live — artifacts land in experiments/bulb_fable/runs/<r>/ # deliverable: workspace/solution/solve.py · prompt: task/ · record: run.json tail -f experiments/bulb_fable/runs/<r>/workspace/.agent/transcript.jsonl

From here, 02 · Examples is the cookbook: ablation arms, run settings, and model comparisons.

What keeps it honest

Tasks come from registered, verified configs Every registered scene–robot pairing has been solved at least once, so an agent is never handed an impossible world.
Nothing to cheat with The container holds no solutions, no verifiers, no demo scripts; the benchmark is read-only and the network reaches only the model API and the package index.

02Examples

Ablations compose the two procedures: building worlds (§04) for world-level arms and running agents (§05) for prompt-level arms. The pattern is always: build one world per arm, run the same agent and condition N times against each, compare the run.json records — the receipts prove the arms differed in exactly the intended way.

Snapshot ablation — does rollback ability matter?

# build the two arms: identical except env.set_states() raises in the second python3 eval/scripts/build_env.py --name bulb --stage bulb:franka python3 eval/scripts/build_env.py --name bulb_nosnap --stage bulb:franka --no-set-states # run each arm N times (same model, same condition) python3 eval/scripts/run_agent.py experiments/bulb --model claude-fable-5 --run trial1 python3 eval/scripts/run_agent.py experiments/bulb_nosnap --model claude-fable-5 --run trial1 # … repeat with --run trial2, trial3, … # any difference is attributable to rollback ability alone: # resolved.json differs in one field (set_states) · runs differ in nothing else

Controller-tier ablation — how much does the controller help?

# one world per tier, via the third slot of --stage # (a tier must be a registered preset — the feasibility gate) python3 eval/scripts/build_env.py --name bulb_osc --stage bulb:franka:osc python3 eval/scripts/build_env.py --name bulb_joint --stage bulb:franka:joint python3 eval/scripts/run_agent.py experiments/bulb_osc --model claude-fable-5 --run trial1 python3 eval/scripts/run_agent.py experiments/bulb_joint --model claude-fable-5 --run trial1 # each world is frozen to its own mode (switching raises); gains + strategy stay free

Prompt ablation — same world, different disclosure

# no rebuild: arms differ only in the condition yaml passed to the runner. # e.g. default.yaml teaches the snapshot workflow; a bare yaml (hints: []) does not python3 eval/scripts/run_agent.py experiments/bulb --model claude-fable-5 --run hinted1 python3 eval/scripts/run_agent.py experiments/bulb --config eval/prompts/configs/<bare>.yaml --run bare1 # run.json records hints/rules per run; the world hash proves both arms shared one world

Same world, different run settings

# compare models — no new worlds, no new conditions python3 eval/scripts/run_agent.py experiments/bulb --model claude-fable-5 --run fable1 python3 eval/scripts/run_agent.py experiments/bulb --model claude-opus-5 --run opus1 # compare agents (credential for each in your shell env) python3 eval/scripts/run_agent.py experiments/bulb --agent codex --model <id> --run codex1 # budget as a variable, and pinning the GPU on a multi-GPU host python3 eval/scripts/run_agent.py experiments/bulb --model claude-fable-5 --budget-min 60 --run quick1 python3 eval/scripts/run_agent.py experiments/bulb --model claude-fable-5 --budget-min 240 --gpu 1 --run long1 # every run is archived separately: experiments/bulb/runs/<run-name>/

Transfer — sequence of stages, shared workspace

# one experiment, ordered stages; the agent keeps /workspace across stages python3 eval/scripts/build_env.py --name screw_transfer --stage bulb:franka --stage nut_thread:franka # the per-stage sequence runner is future work — run_agent runs single-stage worlds only

Arms combine freely — e.g. --stage bulb:franka:joint --no-set-states is a joint-tier world with snapshots blocked. Model ablations need no new worlds at all: rerun the same commands with --agent codex --model <id>.

03Build the docker images

Everything an agent run needs except the benchmark itself, baked once into layered images: the Isaac simulator stack in a ready venv, and the agent CLIs on top. Benchmark changes never require a rebuild.

The images

Install

# 0 · host prerequisites — docker, NVIDIA container toolkit, CDI spec. # CDI is mandatory (legacy --gpus breaks Vulkan/RTX): see eval/docker/INSTALL.md # after every NVIDIA driver upgrade: sudo nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml # 1 · sanity checks (small image, GPU passthrough, agent CLI): make test-image && make test-gpu && make test-claude # 2 · the real images # l0: the Isaac baked venv — 30–60 min, once make l0 # warm: boots the venv once, warms the shader cache make warm # l1: the agent-CLI layer — minutes make l1 CC_VERSION=$(npm view @anthropic-ai/claude-code version)

All make targets live in eval/docker/Makefile. Credentials are never baked into images — they enter later, per run, through environment variables.

04Build the experiment folder

One command turns a registered task into a self-contained, boot-proven folder on disk — the world the agent will later be locked into.

# requires the repo's .venv (robobench + Isaac Lab) — but no activation: # the script re-execs itself into it python3 eval/scripts/build_env.py --name bulb_smoke --stage bulb:franka # --list show all registered presets # --stage scene:robot[:controller] — controller defaults osc > impedance > joint # --no-set-states ablation: disable snapshot-restore; solve from reset() forward # --no-freeze-controller allow switching control modes (default: frozen to the preset) # transfer test: repeat --stage to build an ordered sequence — e.g. skills carried to a new scene: python3 eval/scripts/build_env.py --name screw_transfer --stage bulb:franka --stage nut_thread:franka # each stage gets its own bench/; the agent keeps its workspace files from stage 01 into stage 02

What it does

resolveintent → registered preset, else fail with the menu of what exists
extractminimal benchmark tree: no other suites, no demo scripts, only the assets this task needs; solve-provenance comments scrubbed
patchone-time edits to the copied code that block functions the agent could otherwise exploit — control-mode switching (blocked by default), snapshot restore (--no-set-states). The mount is read-only, so a block cannot be undone.
boot-provelaunch the sim from the extracted tree and reset the actual preset — no world ships unbooted
receiptcontent hash + repo revision + argv, so every result is attributable to exact code

What lands on disk

experiments/bulb_smoke/ ├─ resolved.json receipt: argv · preset · hashes · repo revision ├─ MANIFEST human-readable summary ├─ stages/01_bulb_franka/ │ ├─ bench/ minimal benchmark tree, boot-proven (~141 MB for bulb) │ └─ describe.md scene + robot description, harvested at boot └─ runs/ created later, one per agent run

Everything environmental fails here, at build time — unregistered combos, missing assets, broken presets. At agent time, a failure is the agent's. The build produces the world only: the prompt folder is assembled per run (§05), with describe.md as its raw material.

05Run experiments

A run pairs one built world with one prompt condition. The world is fixed; the hints are chosen per run — so a single experiment folder hosts bare runs, hinted runs, and everything between, all against the byte-identical tree. One run = one disposable container, killed at its budget.

# credential — from your shell, never stored (or ANTHROPIC_API_KEY / OPENAI_API_KEY) export CLAUDE_CODE_OAUTH_TOKEN=… # run with the default condition (eval/prompts/configs/default.yaml) … python3 eval/scripts/run_agent.py experiments/<exp> # … or with a chosen condition yaml python3 eval/scripts/run_agent.py experiments/<exp> --config eval/prompts/configs/<cond>.yaml # the CLI is infrastructure only: --agent claude|codex · --model … · --gpu N · --budget-min … · --dry-run # hints / rules live ONLY in the condition yaml — authored, never ad-hoc flags # run_agent = the default runner: one scene + one task; sequence runners are future scripts

The /task folder — assembled fresh for every run

runs/<r>/task/ mounted ro at /task; instructions.md is fed to the agent CLI ├─ instructions.md contract + index of what exists (+ workspace note on stage 02+) ├─ task.md auto-generated: scene + robot description, goal, build snippet ├─ rules/… selected disclosures — never automatic └─ hints/… selected hints; both libraries live in eval/prompts/

Everything except the auto-generated task.md is hand-authored library content, included only when the yaml/CLI selects it. The prompt may withhold (an unselected rule = undisclosed restriction) but never lie: a rule or hint contradicting the world's receipt refuses to launch. run.json records hints, rules, and a hash per task file. Higher-level orchestration (repeats, agent matrices, stage sequencing) stays future work.

Caveat: only the prompt varies per run. Restrictions like --no-set-states are baked into the tree at build time; the runner merely discloses them. Same scene free vs. restricted = two built experiments.

The container contract — what the agent sees

stages/01_…/bench/
→ ro
/bench import robobench = this tree, nothing else
runs/<r>/task/
→ ro
/task the per-run prompt folder (instructions · task · rules · hints)
runs/<r>/workspace/
↔ rw
/workspace the only writable dir; visible on the host live
docker volume rb-ovcache
↔ rw
/ovcache shared shader cache
baked in the image, not mounted: /opt/venv (Isaac) · agent CLIs — and nothing of the repo

The repo, your experiments, solutions, and .git do not exist inside the container. run_agent.py runs open-network for development; results that count go through eval/docker/compose.agent.yaml, whose egress allowlist admits only the model API and the package index (GitHub blocked — the public repo's history cites solve-calibrated configs).

06Auto-grade not built yet

The shape is decided; the details are deliberately not. What is fixed: grading replays the submitted solution in a second isolated container — the exact same world as the agent's, plus the private verifiers, which never appear in the agent's container. The agent may do anything during its run; only what passes the replay counts.

Verifier design, metrics, and scheduling are open. Runs archive everything raw so no option is closed.

Proven by oracle replay — e.g. the bulb solve, seated in-sandbox on video.
