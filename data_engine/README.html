01Overview

A coding agent solves a robobench task once. The data engine multiplies that single verified solve into a large, diverse, per-episode-verified demonstration dataset.

Three decoupled stages: diversify — agents write the code that adds diversity (scenes, strategies, phases, resets); generate — one generic launcher mass-produces batched episodes from whatever is authored; verify — the scene's grader stamps a verdict on every episode. Verification is also the feedback on the code: agents test-launch small batches mid-session, and each batch's success rate is documented — informing further authoring and repair.

Hierarchical diversification

The engine diversifies the scene and the solve along a hierarchy where each level contains the next: one scene hosts many strategies; each strategy breaks into phases, re-enterable from many sampled states; dynamics perturb every rollout; every rollout re-renders visually. Each level can be run independently — none is mandatory, none waits on another, and the downstream experiment picks the subset it needs.

03Diversification levels

One subsection per level of the hierarchy — the rules, the examples, and the checks each level runs at acceptance.

L1 · scene

Gentle modifications of the world — editing the scene code, optionally the configs and grader; parts that need dedicated expert checks stay untouched. In scope: irrelevant objects (an apple beside the bulb — collision-safe placement, assets from the prebuilt pipeline); the work surface (a different table height or condition, or a more task-suited table). Where a change shifts what success looks like, the scene's check functions and grader are rewritten to match. Out of scope for now: the hard parts — thread mechanics, physics config, and mechanisms like the weld gate stay as the suite ships them.

L2 · strategy

A strategy is a way to do the task, delivered in its solve.py, usually separated into several phases, e.g. pick → place → thread. It varies at three grains: parameters of the solve, e.g. forces, speeds, clearances, named as UPPERCASE constants at the top of solve.py (the file's values are the nominal), optionally banded in a SOLVE_PARAMS dict beside them (mirroring the scene's PHYSICAL_PARAMS) — generate draws ONE set per batch and writes it onto the module before calling solve(env), whose signature never changes; small modifications, e.g. execution order where several are valid, preference choices, grasp site; big changes: a genuinely new way to solve the task, e.g. assembling a table with two arms, one strategy has a single arm do the assembly while the other only reorients the table; a new strategy hands the leg over and both arms thread.

L3 · phase

Once a strategy is finished, each of its phases becomes an entry point: the strategy's solve.py enters there and runs to task-done, and the phase's reset conditions (reset/<name>.py) propose what the entry state looks like, e.g. restore a recorded mid-task state and jitter it, relocate a free object alone, or move a grasped object rigidly together with the hand. Phases are established, not assumed: init bakes no phases/ folder at all — the solve as delivered runs unmodified from the scene's own reset, whatever its shape. An L3 agent session creates phase cells (phases/phase_N/), each a self-contained proposal of how to divide and enter the solve, carrying its own solve_by_phase.py — solve.py itself is never modified — accepted only if the phase's test batch yields.

L4 · dynamics

Random perturbations to actions and physical parameters, e.g. actuation noise, friction, mass. The solve's own feedback control mitigates them, and that recovery behavior is what gets recorded: the perturbed action is executed, the clean action is the label. No agent involved, just batched solves.

L5 · visual

Generic, cheap, and free of physics: once a trajectory is solved and recorded, replaying its states lets visual changes apply without affecting the dynamics, e.g. camera position, textures, lighting, background. Each variant costs render time only, and it works retroactively on every episode ever recorded.

04Generating data

Generation takes a scene and a solver (strategy + phase entry) and turns them into many trajectories — one generic launcher, batched rollouts, every episode graded, and the scene's PHYSICAL_PARAMS bands sampled automatically: one world per env, env 0 nominal. No task-specific logic anywhere in the launcher.

05Replay & export

L5 in practice: recorded states re-render to RGB frames without touching the dynamics — retroactively, on every episode ever recorded — then pack into a LeRobotDataset for VLA training.

Render (scripts/render.py — boots Isaac)

.venv/bin/python data_engine/scripts/render.py --headless \ <…/data_gen/<gen_name>> --batches bf_scene3

That is the whole normal run — the defaults (8 parallel envs, one frame per control latch, 640×480, every camera the scene and robot declare) are what a dataset render uses. Everything tunable is in the args table below.

Generation records states only — rendering stays a separate, retroactive pass (any batch, any time, any camera). For convenience the two chain: generate.py --render [--render_args "…"] replays the freshly graded batch in its own process.

Kinematic replay: the env rebuilds from the cell's local scene (exactly like generate), then every rendered frame is a restored recorded state — env.set_states on num_envs episodes at once, one TiledCamera pass rendering all of them together (that is where the parallelism lives). Physics decides nothing. The scene's post_step runs on each restored state before the render, so state-coupled visuals — the bulb's glow — land in the correct frame. Episodes recorded on any env grid replay anywhere: positions shift onto the replay slots, anchored on the deterministic robot base.

  • Outputs, per (episode, view): imgs/<view>/frame_%06d.jpg (the dataset frames — the layout's imgs/ slot), imgs/render_<view>.json (frame indices + the actual per-episode camera + joint names + visual draw: the export contract, per view so several views/looks coexist), imgs/preview_<view>.mp4 (time-lapsed, for eyeballing). Per batch: replay_sheet_<view>.png, an episodes × time contact grid.
  • Cameras are declared, not flag defaults: the scene's CAMERAS are external views (eye/target env-origin-relative on the work surface — viewpoint knowledge authored next to the geometry it frames), the robot's CAMERAS are ego views (a link key mounts the camera on that body — it rides the link through the replayed motion; embodiment knowledge). All declared views render simultaneously, one TiledCamera each, in the same pass. Per-view bands randomize the pose with the engine's sampling grammar on {eye,target}_{x,y,z} (nominal = the declared value): drawn per episode (Halton on the episode's run position), applied before the chunk's warmup, frozen for the episode — every episode gets its own fixed, reproducible camera, stamped into its render_<view>.json.
  • The renderer has state of its own ("visual cache"): the RTX temporal denoiser accumulates across frames, so teleports leave ghost trails and a fresh boot renders its first frames dark. --warmup (default 12) burns throwaway renders at every chunk start. And Kit shows what PhysX had at its last step — the one sim.step(render=True) per frame is what carries restored transforms into the renderer.
  • Visual diversification is scene-owned, mirroring L4's world physics: the cell's scene.py declares VISUAL_PARAMS bands (same distribution grammar as PHYSICAL_PARAMS, the cfg default = the nominal look) — one file, next to the knowledge that justifies the ranges, and the L1 agent authors it with the rest of the cell. --visual_draw k samples the bands at Halton index k into one stage-wide look per render pass (lights and ground are shared prims, so a pass can't mix looks); K looks of the same episodes = K runs, kept apart with distinct --cam names, and the draw + values are recorded into render_<cam>.json. The draw applies at both moments, so knobs need no tags: values are written onto the scene cfg before the build — build-consumed fields (a table preset, a backdrop usd) take effect there with zero extra code — then handed to scene.apply_visual_params(env, values) after it for the live subset (light/texture attribute writes, material rebinds; a knob with no branch there already did its work at build). For looks that don't band-ify there is the escape hatch: --visual file.py with setup(env) (once, after the build and after the banded look) and per_frame(env, t) (before each rendered frame).
  • One scene per process; inputs spanning several scene cells split into one subprocess per scene automatically.

One standalone robot per frame — Isaac has no true parallel rendering

Unlike Genesis, MJX + Madrona, or ManiSkill — which batch-render N independent worlds — Omniverse RTX renders one shared USD stage: a TiledCamera is a single render product packing N viewpoints of that same stage, so every camera sees every environment. This is a documented limitation, still current (verified 2026-08): the TiledCamera docs note the camera renders all other parallel environments into the image (IsaacLab PR #1246), and the request for per-env-only rendering (issue #4021, Nov 2025) closed with no supported feature — USD visibility is stage-global, not per-camera.

The standard fix — used by NVIDIA's own image pipelines — is geometric: keep every neighbor beyond the camera's far clip plane, where geometry is discarded before rasterization. Zero neighbor pixels can render, which is pixel-identical to independent worlds, at full tiled-rendering speed. In the wild: DEXTRAH runs clipping_range=(0.01, 2.0) at env_spacing=2.0; GR00T-VisualSim2Real runs (0.1, 20.0) at env_spacing: 20.

  • Here: --env-spacing (default 50 m) > far clip (40 m) — a 10 m margin, so isolation holds for any camera pose, not just cameras centered in their cell. Replay owns its grid (recorded states shift onto the replay origins), so the spacing costs nothing.
  • The shared ground plane is auto-enlarged to grid extent + far-clip margin, or far-flung envs would float over sky.
  • Side effect: the background beyond 40 m is dome-light sky (a plain horizon line) — the same look DEXTRAH/GR00T training images have. A richer backdrop is a per-env asset (an L1 scene edit or the --visual hook), not a renderer setting.
  • Setting --env-spacing at or below the far clip prints a warning and neighbors reappear — the true-isolation alternative (one env per process) costs a ~90 s Kit boot per episode and loses the tiling.

Export (scripts/export_lerobot.py — no Isaac)

~/Documents/Research/lerobot/.venv/bin/python data_engine/scripts/export_lerobot.py \ <…/data_gen/<gen_name>> --repo-id cosigen/bulb_franka_osc --task "…"

The exporter runs in the LeRobot/openpi environment, not the Isaac environment. It reads verified episode metadata, traj.npz, rendered frames, and each render_<view>.json frame-index contract. The current pi0.5 schema uses the first rendered non-ego view as image, the first link-mounted view as wrist_image, eight joint-state values, seven action values, and the required --task instruction. Every visual draw directory (imgs/, imgs_drawN/) becomes a separate dataset episode over the same verified motion. Failed episodes are skipped unless explicitly included.

Chaining from generation: generate.py --render runs render.py on the fresh batch after grading, and --render_args "…" forwards any of the render flags above.

Unify solver-parameter generation with eval's parameter search

eval already tunes solve constants: eval/tools/parameter_search.py (the cosigen-parameter-optimize skill) runs CMA-ES over a space={"NAME": (lo, hi)} declaration with per-env parameter arrays in ~512 parallel envs. The engine's SOLVE_PARAMS draws one set per batch from hand-set bands over the same kind of constants. Study unifying the two: shared constant names and space/band declaration, and the search's converged region as the evidence that sets SOLVE_PARAMS bands — search finds the safe region, generation samples inside it.

Generate batches across machines

data_engine/scripts/orchestrate.py is the infrastructure-neutral conductor for one campaign: six HARD gates, each on its own 12 h clock, stopping the campaign with the failed rung named when a clock runs out (PRECHECK_FAILED / STAGE_FAILED): pre-checks (the delivered solve must succeed nominally, replay, and complete a 512-env batch with a success that replays; repair/vectorize sessions repeat until it does), then the ladder of exact nested trajectory sets 1 → 5 → 20 → 50 → 200 → 600 — scene / strategy / phase authoring stages each deliver <level>_set.json (the previous set whole plus a round-robin fill across that stage's cells, every kept cell contributing at least one replay-verified episode, byte-identical trajectories never counted twice, episodes counted only while their cell's code is unchanged), the dynamics stage (one base-cell noise certification, then harvest batches round-robin over the phase set's cells, each batch's successes replay-verified at once → physics_set.json of exactly 200), the visual stage (scene contracts, then a pass-major render queue of exactly 200 × 3 looks), status, and manifest. Cluster schedulers remain separate: they launch one orchestrator per task, supply an agent command, and persist the campaign directory. Batches are append-only and seeds/draw indices are explicit, so a campaign resumes from its own ledger and batch metadata.
